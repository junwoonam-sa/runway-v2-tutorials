# Stage 0 — 환경 정보와 인증 키, OpenBao

> **이 단계가 끝나면**
> - 뒤에서 계속 쓸 값 다섯 개가 손에 있습니다
> - LLM API 키로 게이트웨이를 직접 호출해 봤습니다
> - OpenBao에 KV-v2 엔진을 마운트하고 시크릿을 저장했습니다

소요 30분. 콘솔 작업이 대부분입니다.

---

## 0-1. 환경 정보 적어 두기

Runway 콘솔에 로그인합니다. 주소는 `https://runway.<도메인>` 입니다.

이 표를 채우세요. 뒤의 모든 단계가 여기를 참조합니다.

| 이름 | 어디서 확인 | 내 값 |
|---|---|---|
| 베이스 도메인 | 브라우저 주소창의 `runway.` 뒤 | `_______________` |
| 프로젝트 ID | 프로젝트 선택 후 URL 또는 프로젝트 상세 | `_______________` |
| LLM 게이트웨이 | `https://llm.<도메인>/v1` | `_______________` |
| Gitea | `https://gitea.<도메인>` | `_______________` |
| OpenBao | `https://openbao.<도메인>` | `_______________` |

> **프로젝트 ID는 정확히 적으세요.** 네임스페이스 이름이자 OpenBao 네임스페이스
> 이름이고, Stage 4에서 Qdrant 주소를 만들 때 그대로 들어갑니다.

빈 파일에 이렇게 적어 두면 편합니다. **커밋하지 마세요.**

```
DOMAIN=example.com
PROJECT=my-project
LLM_BASE_URL=https://llm.example.com/v1
```

## 0-2. 키 세 개 — 서로 다른 것입니다

콘솔 우측 상단 계정 메뉴 → **설정** → **액세스 키(Access keys)**.
탭이 세 개 있고, 셋은 **완전히 다른 시스템이 발급한 다른 자격증명**입니다.

| 탭 | 발급 주체 | 쓰는 곳 | 생김새 |
|---|---|---|---|
| API 키 | Keycloak (오프라인 토큰) | 플랫폼 API, MLflow, Airflow, 추론 엔드포인트 | `eyJ...` |
| **LLM API 키** | LiteLLM (가상 키) | **LLM 게이트웨이** | `sk-...` |
| S3 키 | SeaweedFS | 오브젝트 스토리지 | 액세스 키 + 시크릿 |

**이 튜토리얼이 반드시 필요로 하는 것은 LLM API 키 하나입니다.** 나머지 둘은 Stage 5의
선택 경로에서만 쓰입니다.

### LLM API 키 발급

`LLM API 키` 탭 → **생성**. 값이 드로어에 한 번 뜹니다.

> ⚠ **값은 딱 한 번만 보입니다.** 목록 API는 마스킹된 값만 돌려줍니다. 놓치면
> 지우고 다시 만드는 수밖에 없습니다. **지금 안전한 곳에 복사해 두세요.**

### API 키를 발급한다면 — 알아 둘 것

이 튜토리얼에는 필수가 아니지만, 발급한다면 다음을 알고 하세요.

> ⚠ **두 번째 API 키를 만들면 첫 번째가 조용히 폐기됩니다.** 한도가 1이고 전략이
> `rotate`이라, 오류도 확인 창도 없이 예전 키가 무효가 됩니다. 그 키를 쓰던 다른
> 무언가가 있다면 그것부터 멈춥니다. 콘솔은 이유를 알려 주지 않습니다.

## 0-3. 게이트웨이가 살아 있는지, 모델 이름이 무엇인지 확인

**이 확인을 건너뛰지 마세요.** Stage 2에서 앱이 답을 못 하는 경우의 대부분이 여기서
5초면 드러납니다.

먼저 인증 없이 되는 헬스 체크:

```bash
curl -s https://llm.<도메인>/health/liveliness
```

그다음 **모델 목록**. 이것이 핵심입니다.

```bash
curl -s -H "Authorization: Bearer sk-여기에키" https://llm.<도메인>/v1/models
```

```json
{"data":[{"id":"qwen2-5-0-5b-instruct","object":"model", ...}]}
```

`id` 값이 앱 설정의 `LLM_MODEL`에 그대로 들어갑니다.

> **모델 이름은 추측할 수 없습니다.** 관리자가 LiteLLM 설정에 손으로 적어 넣은
> 문자열이라 규칙이 없습니다. 그리고 기본 설치에는 항목이 하나뿐인데 **그 백엔드가
> 아직 없을 수도 있습니다** — 목록에는 보이지만 호출하면 실패하는 상태입니다.

실제로 대화가 되는지도 한 번:

```bash
curl -s -X POST https://llm.<도메인>/v1/chat/completions \
  -H "Authorization: Bearer sk-여기에키" \
  -H "Content-Type: application/json" \
  -d '{"model":"<위에서 본 id>","messages":[{"role":"user","content":"한 문장으로 인사해줘"}]}'
```

| 응답 | 뜻 | 조치 |
|---|---|---|
| 정상 JSON | 됨 | 다음으로 |
| `401` | 키가 거부됨 | `sk-`로 시작하는지, 방금 지운 키가 아닌지 |
| `404` + model | 모델 이름 오타 | `/v1/models` 로 다시 확인 |
| 연결 안 됨 | 도메인이 다르거나 게이트웨이가 안 뜸 | `/health/liveliness` 부터 |

**임베딩 모델도 있는지 봐 두세요.** 위 목록에 `bge`, `embedding`, `e5` 같은 이름이
있으면 Stage 4가 훨씬 간단해집니다. 없어도 됩니다 — 그때는 앱 안에서 임베딩합니다.

## 0-4. OpenBao — 시크릿을 코드 밖에 두기

### 왜 이 단계가 있나

LLM 키를 `values.yaml`에 적으면 애플리케이션을 볼 수 있는 사람 모두가 그 값을 봅니다.
이미지에 굽는 것은 더 나쁩니다 — 이미지를 pull할 수 있는 누구에게나 남습니다.

OpenBao에 넣으면 값이 **파드가 뜰 때 파일로 주입**됩니다. 차트에도, 이미지에도,
git에도 없습니다. Stage 1의 Code Server와 Stage 5의 챗봇이 **같은 시크릿을** 이렇게
받아 갑니다.

### 알아 둘 것 두 가지

> **엔진은 자동으로 만들어지지 않습니다.** 프로젝트 OpenBao 네임스페이스는 생기지만
> KV-v2 엔진은 **프로젝트 멤버가 직접 마운트**해야 합니다. 플랫폼이 정해 준 엔진
> 이름이 없어서, 차트가 엔진 경로를 값으로 받는 것입니다.

> **로그인할 때 Namespace 필드에 프로젝트 이름을 넣어야 합니다.** OIDC 인증 방법이
> 루트가 아니라 프로젝트 네임스페이스 안에 있습니다. 비워 두면 로그인이 안 됩니다.

### 로그인

콘솔의 **Built-in Apps** 탭 → **OpenBao** 카드로 들어가면 SSO 경로를 탑니다.
(직접 `https://openbao.<도메인>` 으로 가도 되지만, 카드 경로가 안전합니다.)

로그인 화면에서:

| 필드 | 값 |
|---|---|
| Method | **OIDC** |
| Namespace | **프로젝트 ID** ← 반드시 |
| Role | 비워 둠 (`default`가 적용됩니다) |

### KV-v2 엔진 마운트

**Secrets Engines** → **Enable new engine** → **KV** → Version **2**.

Path에 이름을 정합니다. 이 튜토리얼은 `tutorial`을 씁니다.

```
Path:    tutorial
Version: 2
```

이름은 자유지만, **정한 이름을 적어 두세요.** 차트의
`runway.openbao.secretEngine` 에 그대로 들어갑니다.

### 시크릿 만들기

방금 만든 엔진 → **Create secret**.

```
Path for this secret:  llmchat

키/값:
  LLM_API_KEY = sk-여기에아까그키
```

나중에 공유 비밀번호를 쓸 거라면 같은 시크릿에 하나 더 넣어 둡니다.

```
  ACCESS_PASSWORD = 아무거나-긴-문자열
```

한 시크릿에 둘 다 넣는 이유는 단순합니다 — 주입되는 파일이 하나면 되고, 관리할
경로가 하나입니다.

### 경로 규약 — 헷갈리는 지점

UI에서 만든 것이 `tutorial` 엔진의 `llmchat`이면, API 경로는 이렇게 됩니다.

```
tutorial/data/llmchat      ← 읽기 경로 (KV-v2의 /data/ 는 규약)
tutorial/metadata/llmchat  ← 메타데이터
```

**`/data/`는 차트가 붙입니다.** 값에 넣는 것은 엔진 이름(`tutorial`)과 시크릿
이름(`llmchat`) 둘뿐입니다. 손으로 어노테이션을 쓰면 선언 경로와 템플릿이 읽는
경로가 어긋나는 실수가 잦습니다.

### 권한에 대해

| 역할 | 엔진 마운트 | 시크릿 생성/수정 | 버전 삭제 |
|---|---|---|---|
| admin | ✓ | ✓ | ✓ |
| member | ✓ | ✓ | ✗ |
| viewer | ✗ | ✗ (아무것도 못 봄) | ✗ |

member면 이 튜토리얼을 전부 진행할 수 있습니다.

## 여기까지 되면 성공

- [ ] 도메인·프로젝트 ID·게이트웨이 주소를 적어 두었다
- [ ] LLM API 키(`sk-`로 시작)를 발급하고 안전한 곳에 복사했다
- [ ] `curl .../v1/models` 가 모델 이름을 돌려주고, 그 이름을 적어 두었다
- [ ] `curl .../v1/chat/completions` 가 답을 돌려주었다
- [ ] OpenBao에 KV-v2 엔진 `tutorial` 을 마운트했다
- [ ] 그 안에 시크릿 `llmchat` 을 만들고 `LLM_API_KEY` 를 넣었다

## 막히면

| 증상 | 원인 | 조치 |
|---|---|---|
| OpenBao 로그인이 안 됨 | Namespace 필드가 비어 있음 | 프로젝트 ID를 넣으세요 |
| `auth/oidc/...` 404 | 프로젝트 OpenBao 네임스페이스가 아직 없음 | 사용자가 고칠 수 없습니다. 관리자에게 프로젝트 dependency 상태 확인 요청 |
| Secrets Engines가 안 보임 | viewer 역할 | member 이상이 필요합니다 |
| 게이트웨이 401 | 키가 `sk-`가 아니거나 삭제됨 | API 키를 잘못 넣었는지 확인 |
| 모델 목록은 나오는데 호출이 실패 | 모델의 백엔드가 없음 | 관리자에게 문의 — 그 사이에는 [로컬 실행](../../README.md)으로 진행 가능 |

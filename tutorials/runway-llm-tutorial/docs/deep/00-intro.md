# 00. 시작하기 전에

읽는 데 10분. 여기 있는 세 가지를 헷갈리면 뒤에서 계속 막힙니다.

---

## 1. 프로젝트 ID 하나가 네 곳에서 같은 이름으로 쓰입니다

Runway에서 **프로젝트**는 격리 단위입니다. 프로젝트를 만들면 이름이 같은 것이
네 개 생깁니다.

| 무엇 | 이름 |
|---|---|
| 쿠버네티스 네임스페이스 | 프로젝트 ID |
| S3 버킷 | 프로젝트 ID |
| OpenBao 네임스페이스 | 프로젝트 ID |
| MLflow 실험 이름 접두사 | `<프로젝트 ID>.` |

그래서 인클러스터 주소를 쓸 때 `<서비스>.<프로젝트 ID>.svc.cluster.local` 이 됩니다.
프로젝트 ID를 모르면 Stage 4의 Qdrant 주소를 못 만듭니다 — Stage 0에서 제일 먼저
적어 둡니다.

---

## 2. 애플리케이션 = 등록된 Helm 리포지토리의 차트

이것이 가장 자주 오해되는 지점입니다.

**Runway는 git 저장소를 차트로 읽지 않습니다.** 소스를 Gitea에 push하는 것과,
차트를 패키징해 Helm 레지스트리에 올리는 것은 **별개의 작업**입니다. 소스만 올리고
애플리케이션을 만들려고 하면 리포지토리 등록 단계에서 반드시 실패합니다.

Stage 5에서 하는 일이 이렇게 나뉩니다.

```
소스 코드 ──▶ Gitea 저장소            (사람이 읽고 고치는 것)
소스 코드 ──▶ 컨테이너 이미지 ──▶ Gitea 컨테이너 레지스트리   (파드가 실행하는 것)
차트      ──▶ .tgz          ──▶ Gitea Helm 레지스트리        (Runway가 읽는 것)
```

세 곳이 각각 다른 자격증명 스코프를 요구합니다. Stage 5에 표로 정리해 두었습니다.

---

## 3. 생성 ≠ 배포

애플리케이션 생성 폼을 제출하면 **설정 행만 만들어지고** 상태가 `terminated`로
들어갑니다. 워크로드는 아무것도 뜨지 않습니다.

상세 페이지의 **배포(Deploy)** 버튼을 눌러야 실제로 배포됩니다.

"만들었는데 아무 일도 안 일어나요"의 대부분이 이것입니다.

## 이 튜토리얼이 만드는 것의 구조

```
   프로젝트 네임스페이스
   ┌────────────────────────────────────────────────────────────┐
   │                                                            │
   │  ┌──────────────────┐        ┌──────────────────────────┐  │
   │  │  Code Server     │        │  llm-tutorial (커스텀 앱) │  │
   │  │  (Stage 1)       │        │  (Stage 5)               │  │
   │  │                  │        │                          │  │
   │  │  개발은 여기서   │        │  FastAPI ─stdio─ MCP서버  │  │
   │  └────────┬─────────┘        └────┬──────────────┬──────┘  │
   │           │                       │              │         │
   │      /home/coder PVC              │              │         │
   │                                   │              ▼         │
   │                                   │      ┌───────────────┐ │
   │                                   │      │  Qdrant       │ │
   │                                   │      │  (Stage 4)    │ │
   │                                   │      └───────────────┘ │
   └───────────────────────────────────┼────────────────────────┘
                                       │
                       ┌───────────────▼──────────────┐
                       │  LiteLLM (플랫폼 공용)        │
                       │  runway-applications 네임스페이스 │
                       └──────────────────────────────┘
```

Code Server, Qdrant, 챗봇 셋 다 **프로젝트 애플리케이션**입니다. 앞의 둘은 Runway가
제공하는 템플릿에서 설치하고, 마지막 하나는 우리가 차트를 만들어 올립니다. 세 개
모두 같은 목록에, 같은 방식으로 나타납니다.

LiteLLM만 프로젝트 밖에 있습니다 — 플랫폼이 공용으로 운영하는 것이고, 우리는
`llm.<도메인>` 또는 인클러스터 주소로 부르기만 합니다.

## 자원 이야기 — 미리 알아두면 좋습니다

프로젝트 쿼터는 생각보다 빨리 찹니다. 이 튜토리얼이 요청하는 양은 대략:

| 워크로드 | CPU 요청 | 메모리 요청 | 디스크 |
|---|---|---|---|
| Code Server | 500m 안팎 | 1Gi 안팎 | 10Gi (홈) |
| Qdrant | 500m | 1Gi | 1Gi |
| 챗봇 앱 | 100m | 256Mi | (선택) 5Gi |

CPU 2코어짜리 프로젝트라면 이 셋으로 이미 빠듯합니다. 남은 양은 이렇게 봅니다:

```bash
kubectl -n <프로젝트 ID> describe resourcequota
```

`exceeded quota: requests.cpu` 로 파드가 거부되면 그때 볼 곳입니다.
